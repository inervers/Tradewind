# Tradewind 客户名单内跟进功能设计

日期：2026-10-03

状态：用户已确认；2026-10-03 源码实现与自动验收已完成，未构建发行包。

## 1. 目标与已确认范围

让业务员在客户名单中知道上次沟通的内容、下一步事项和再次联系的日期，无需另开表格。用户已选择将入口放在客户名单内部，不新增侧栏 Tab。

第一版包含：

- 客户行的“跟进”按钮和跟进详情面板。
- 人工沟通记录：时间、渠道、结果、内容。
- 每位客户一个有效的下次跟进安排，支持完成、更改和取消。
- 全部、今日待跟进、已逾期、未安排筛选。
- 合并人工记录、安排变更和已有外联信息的时间线。
- 防止删除客户后编号复用，导致历史错关联。

保留现有客户导入、查重、批量删除、来源筛选、仪器介绍、客户状态、开发信生成、外联审核和发送流程。新功能不改变这些功能的既有业务含义。

本轮不包含自动发信、定时发送、邮箱收件、回复自动识别、桌面通知、后台遥测、团队协作、额外销售阶段、改名、PyInstaller 打包或 Tauri sidecar 构建。不引入新的第三方依赖。

## 2. 当前结构与技术选择

当前客户资料保存在本机 `customers.json`，客户状态只有 `new/sent/replied`。其中 `notes` 包含仪器介绍和客户画像，会用于开发信生成。外联队列使用本机 `tradewind_memory.db`，已经保存创建、打开、提交和人工标记回复的时间。

新增跟进记录不能混入 `notes`，也不进入提示词、生成历史、诊断包或发布样例。

存储方案比较：

| 方案 | 取舍 |
| --- | --- |
| 在现有 SQLite 数据库增加独立跟进表（采用） | 支持事务、历史记录和重复请求防护，不搬迁原有客户资料，不增加运行依赖 |
| 把记录和安排嵌入客户 JSON | 改动表面较少，但每次新增记录都重写客户文件，历史查询和并发保护更复杂 |
| 将全部客户迁入 SQLite | 能统一事务，但改变现有导入、查重和数据读取边界，本轮回归范围过大 |

跟进模块与外联模块共享数据库文件，但使用独立表和独立存储类。跟进功能只读取外联信息，不调用发送、打开 WhatsApp 或状态流转操作。

## 3. 客户名单界面

### 3.1 列表和筛选

- 保留现有标题、统计、来源筛选和批量操作。
- 在工具栏增加“全部 / 今日待跟进 / 已逾期 / 未安排”筛选及对应数量。
- 跟进筛选与 Maps、Webs、手动来源筛选取交集；全选和批量删除只作用于当前显示的客户，沿用现有语义。
- 改变来源或跟进筛选时清空勾选；保存安排导致客户不再符合当前筛选时同步移除其勾选，不能删除已经隐藏的客户。
- 客户名称区域增加紧凑的下一次跟进日期和事项摘要；不增加多个宽表格列，不重复显示仪器介绍。
- 操作区域增加“跟进”按钮。日期和事项较长时截断，完整内容在详情面板显示。
- “未安排”表示当前没有有效安排，包括从未安排、已经完成或已经取消；不会把未来安排归为未安排。
- 日期由后端按运行电脑的当地日期判断，前端使用后端返回的分类。进入页面、窗口恢复焦点及页面停留跨日时刷新，不依赖持续运行的后台提醒服务。

### 3.2 跟进详情面板

采用客户名单内的右侧弹出面板。沿用现有暖纸色、琥珀强调色和圆角，不另建视觉主题。

- 面板标题显示客户名称，底部或顶部始终可以关闭。
- 顶部显示当前安排；中部提供记录沟通和安排表单；下部是可滚动时间线。
- 面板限制在视口内，内部独立滚动。小屏时接近全屏，不要求用户滚回页面顶部操作。
- 支持键盘访问、焦点约束、Esc 关闭和关闭后焦点回到入口按钮。
- 表单有未保存修改时，关闭、切换客户或切换 Tab 均需确认放弃；不把草稿写进 localStorage。
- 保存时禁用重复点击；保存失败保留输入并展示可理解的错误。加载失败提供重试，不用空白列表冒充没有历史。
- 已保存的记录和安排在关闭面板、切 Tab、刷新页面和重启程序后仍存在。

### 3.3 记录沟通

字段：

- 沟通时间：默认现在，允许补录过去；发送包含时区的时间，存储为 UTC 时间戳，显示按电脑当地时间。
- 渠道：邮件、WhatsApp、电话、其他。
- 结果：待回复、已回复、继续沟通、无意向、联系方式无效、一般备注。
- 内容：必填，去除首尾空白，上限 4000 个字符。

记录保存后进入时间线。“一般备注”不作为最近联系时间依据；其他结果是用户人工记录的沟通或联系尝试，不保证客户实际收到。

本版人工记录不自动修改 `new/sent/replied`，不生成外联任务，也不自动把“无意向”转换为禁止联系。原有客户状态和禁止联系名单仍通过各自明确操作维护。

人工记录本版允许新增和确认后删除，不提供原地编辑。录入错误时删除后重录；外联信息不能从跟进面板修改或删除。

### 3.4 下次跟进安排

- 跟进日期使用 `YYYY-MM-DD`，事项必填，上限 500 个字符。
- 每位客户最多有一个有效安排。没有有效安排时可新建；已有安排时按钮显示“更改安排”，不静默新增第二个待办。
- 更改日期或事项在同一事务中关闭旧安排、创建替代安排，保留原计划可追溯信息。
- “完成”只表示待办已处理，不表示消息已发送、客户已回复或交易成功；按钮旁明确说明。如需记录沟通结果，另用记录表单。
- 完成或取消后移出今日/逾期待办，但历史仍在。新安排必须由用户再次显式创建，不自动循环或顺延。
- 允许补录已经过期的日期，并明确标为逾期。

## 4. 数据与模块边界

新增 `app/customer_followup.py`，负责 SQLite 表初始化、人工记录、安排、幂等和摘要查询。不包含 FastAPI、模型、爬虫或发送逻辑。

### 4.1 人工记录表

`customer_followup_records` 保存：自增 ID、客户 ID、客户名称快照、沟通 UTC 时间、渠道、结果、内容、创建时间、请求 ID。

请求 ID 唯一。相同请求 ID 与相同内容重复提交，返回原记录；相同请求 ID 对应不同内容，返回冲突，不覆盖原记录。按客户 ID 和沟通时间建索引。

### 4.2 安排表

`customer_followup_plans` 保存：自增 ID、客户 ID、客户名称快照、日期、事项、状态、被替代安排 ID、创建/关闭时间、请求 ID。

状态为 `active/completed/cancelled/superseded`。部分唯一索引保证每客户只有一个 `active` 安排。创建、更改和关闭均在 SQLite 事务内完成。

创建或更改请求带请求 ID 和预期的当前安排 ID。更改遇到其他窗口已改变的安排时返回冲突，要求刷新，不覆盖较新的操作。重复创建或更改请求返回既有结果；重复完成、取消同一安排返回已完成的对应状态，不影响后来创建的新安排。

### 4.3 API 边界

现有 `/api/customers` 返回结构、客户写入接口和外联接口保持兼容。增加本机跟进接口：

- `GET /api/customers/followup-summary`：现存客户的安排、最近跟进时间及筛选分类，含后端当地日期。
- `GET /api/customers/{customer_id}/followup`：单客户当前安排。
- `GET /api/customers/{customer_id}/followup/timeline`：分页时间线，默认每页 50 条，支持继续加载。
- `POST /api/customers/{customer_id}/followup/records`：新增人工记录。
- `DELETE /api/customers/{customer_id}/followup/records/{record_id}`：删除该客户的一条人工记录。
- `POST /api/customers/{customer_id}/followup/plans`：新建或替代安排。
- `POST /api/customers/{customer_id}/followup/plans/{plan_id}/complete`：完成指定安排。
- `POST /api/customers/{customer_id}/followup/plans/{plan_id}/cancel`：取消指定安排。

所有接口校验客户存在，记录和安排必须属于路径中的客户。不存在返回 404，非法内容返回 422，过期操作或重复请求内容不一致返回 409；不输出原始 SQL、文件路径或业务正文到错误日志。

修改请求复用现有本机 Origin 防护。跟进数据不开放到外部服务。

摘要按现存客户集合批量读取，不能每位客户发一次 HTTP 请求。时间线查询必须先按客户过滤，再分页，不能从全局最近 200 条外联中截取，以免老客户历史被漏掉。

## 5. 外联时间线的证据边界

时间线合并人工记录、安排创建/变更/完成/取消，以及当前外联记录中能够确认的节点。每条具有稳定的来源类型和来源 ID，按发生时间倒序排列。

- 外联创建时间可显示“建立外联任务”。
- WhatsApp 打开时间只能显示“已打开预填页面”，不显示为发送成功。
- 邮件当前为 `accepted` 时显示“服务器已接受”，不显示为送达或已读。
- `sent_manual` 显示“人工确认已发送”。
- 回复时间显示“人工标记已回复”，不能声称从邮箱自动读取了回复。
- `failed/unknown` 保留失败或待核查含义，不进入已确认发送统计。
- 旧外联没有完整状态事件日志。只呈现已知时间和当前状态摘要，不伪造每次重试、更换账号或禁止联系前的状态。
- `submitted_at` 在原实现中也可能用于失败尝试，因此不能只凭非空提交时间推断成功；状态被覆盖而无法确认历史结果时使用中性标签。

外联正文不复制进跟进表。原有发送状态机、审批和重启后的 `unknown` 处理保持不变。本版不新增完整外联事件溯源系统。

## 6. 客户身份、删除与兼容

### 6.1 不复用客户编号

已用合成数据确认：现有 `_next_id` 根据现存名单最大编号分配新编号，删除最大编号后会复用该编号。

仅改变新增客户的 ID 分配：手动新增和 CSV/爬虫导入统一使用 `c-` 加 UUID。现有 `c-001` 等 ID 不改写，产品和模板的编号机制不改动。新格式 ID 保持字符串，原有 UI 和外联引用兼容。

受影响的客户增删改、导入、外联摘要状态同步和跟进写入校验使用同一进程内客户锁，避免读取旧名单后覆盖其他线程的修改，也避免删除与建立安排同时发生。JSON 继续原子写入，不整体替换用户文件。

涉及客户写入和跟进清理时，名单读取失败必须报错，不能把解析失败的默认空列表当成真实空名单再覆盖文件或删除记录。正常的空名单与文件不可读、JSON 损坏必须明确区分。

这能防止今后的串号，不能自动证明旧版已经复用过的客户历史归属。不给旧记录自动改客户 ID、根据姓名猜归属或制造历史数据。

### 6.2 删除行为

拟定规则：用户确认删除客户时，一并删除该客户新增的人工跟进记录与安排；已有生成历史、外联历史和禁止联系名单沿用原行为，不被连带删除。单个和批量删除确认文案明确告知这些边界。

由于客户 JSON 和跟进 SQLite 不在同一事务中：

- 客户锁内先原子删除名单，再清理跟进表。
- 名单写入失败时不清理跟进数据。
- 数据库清理失败时明确提示“客户已删除，跟进记录清理失败”，不得报告完全成功。
- 今日待办和摘要只返回当前存在的客户；孤立安排不会出现，也不会关联到新客户。
- 重复删除同一 ID 会继续尝试清理孤立跟进数据；正常启动时只针对已不存在的客户清理新跟进表中的孤立数据，不清理原有外联历史。
- 启动清理必须先确认名单文件可读、成功解析且客户 ID 有效并唯一；校验失败时跳过清理并报告错误，不能通过现有宽松读取函数的默认空列表判断所有客户已删除。

新增表使用增量建表，不迁移或覆盖客户、产品、模板、照片、配置和旧数据库表。

## 8. 验证与验收

自动化测试使用临时 JSON/SQLite 和虚构客户，不读取或改变用户业务资料，不调用真实模型或 SMTP。

重点覆盖：

1. 人工记录校验、持久化、重复提交和跨客户访问拒绝。
2. 每客户只有一个有效安排；更改、完成、取消和重复请求不会生成重复待办。
3. 两个窗口修改同一安排时，过期请求不覆盖新安排。
4. 今天、昨天、明天和无安排的筛选边界，按受控日期测试。
5. 超过全局外联列表上限后，单客户时间线仍能分页看到其历史。
6. `opened/accepted/unknown/replied` 的显示含义正确，失败尝试不伪装成成功。
7. 删除后重建客户不会复用 ID；既有客户 ID 与历史引用保留。
8. 单个/批量删除的跟进清理、失败提示和重试，不影响外联历史或禁止联系。
9. 修改客户基础资料或外联摘要状态不会覆盖其他资料。
10. 诊断包不包含人工记录、待办内容、客户名称快照或跟进数据库内容。
11. 原有客户导入/查重/批量删除、写信工作流、外联发送和前端构建回归。

网页人工验收使用隔离演示数据，检查视口内滚动、保存失败保留输入、未保存离开确认、来源筛选叠加、重启恢复和小屏布局。未经明确授权不启动使用用户真实数据的演示服务、不发送测试消息。

这一轮完成后交付源码网页端供用户测试，不制作新的 EXE、ZIP 或桌面 sidecar。
