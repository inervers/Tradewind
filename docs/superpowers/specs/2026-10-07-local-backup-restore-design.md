# Tradewind 本地业务备份与恢复设计

日期：2026-10-07

状态：用户于 2026-10-07 确认本书面设计与实施计划；实现及验收进行中。

## 1. 目的与边界

让业务员在升级、换电脑或误操作前主动保存业务资料，在需要时恢复到一个明确的备份时点。客户名单和跟进记录必须一起恢复，不能仅复制客户 JSON 后丢失关联。

已同意的方向：设置页入口、照片可选、不导出 Key 或邮箱授权凭据、恢复前展示日期与数量、保存当前数据的救援备份、二次确认、重启后生效。首版使用快照替换，不做客户或跟进记录的智能合并。

本设计进一步明确的保护规则也需随本文件审阅：保留恢复前仍有效的禁止联系规则；恢复的可发送邮件先核查；不恢复运行任务或未审核入队的写信 checkpoint；不含照片的备份不替换现有照片；恢复后拒绝旧网页的迟到修改。

第一轮只交付源码网页功能，保持当前 Tab 结构、视觉主题和原有业务流程。不做云同步、自动备份计划、远程监控、账号系统、备份加密、Tauri 改造或 sidecar 构建。源码验收完成并由用户确认后，另行更新浏览器绿色包。

## 2. 方案选择

| 方案 | 取舍 |
| --- | --- |
| 整份业务快照替换，重启应用（采用） | 客户 ID、跟进、历史与队列一同回到备份时点；可明确验证并回滚，恢复前需保存当前数据 |
| 合并导入 | 可保留两边新增资料，但客户身份、删除记录、安排和外联状态的冲突规则复杂，容易重复联系；首版不做 |
| 停机后人工复制整个数据目录 | 当前可用的兜底方式，但容易带走 Key、漏复制数据库或选错数据根，不作为非技术用户的常规入口 |

“快照替换”只作用于下述业务白名单，并不替换整份运行目录。禁止联系保护是明确的单项例外，不延伸为通用数据合并。

## 3. 备份内容

### 3.1 默认包含

- `customers.json`：客户基本资料、仪器/缺品备注和人工状态。
- `products.json`、`emails.json`：当前产品库与话术模板。
- `tradewind_memory.db` 的已知业务表：生成历史、外联队列、禁止联系名单、人工跟进记录、跟进删除防重标记、跟进安排及必要索引/序列。
- `crawler_seen.json`：已爬取身份与官网去重记录。

文件不存在与内容为空必须在清单中区分。恢复缺失项目时移走当前对应业务文件，不能让它悄悄保留。客户、产品、模板文件缺失时恢复目标明确写入合法空列表，阻止绿色版重新填入演示数据；爬虫记录缺失时同样使用空列表。数据库不存在时恢复为空业务数据库，并正常执行已知的增量建表流程。

内存库仅接受当前数据目录内的标准 `tradewind_memory.db`。若 `MEMORY_DB_PATH` 指向另一文件，即使它仍在本机，也拒绝本功能并解释需要人工停机备份；不漏掉自定义历史库，也不覆盖外部路径。

### 3.2 可选照片

默认不勾选“包含照片”；界面说明不勾选时照片仍保留在当前电脑，但不会随备份迁移。

勾选后包含 `crawler_photos/` 店铺照片和 `photo_scan/` 手动识别原图，保留目录与文件名，不转码、不再次识别、不重新下载。仅接受当前照片功能支持的 JPEG、PNG、WebP、GIF 普通文件；其他文件不静默丢弃，提示用户处理后重试。目录存在但没有图片也在清单中明确记录。

恢复含照片的备份会替换这两个照片目录；恢复不含照片的备份则原样保留现有照片。两种行为都在预览和确认框说明。店铺照片未按客户 ID 绑定，不根据店名猜测或修改客户关联。

### 3.3 明确不包含

- `.env`、`config.json`、写信/视觉 Key、模型路由设置、公司签名设置、SMTP 账号设置与 Windows 凭据管理器内容。
- 原始日志、诊断包、CSV 导出、中间文档、缓存、旧备份、构建产物及 SQLite WAL/SHM/journal 文件。
- 浏览器未保存表单、localStorage、运行中的任务及未审核入队的单封写信 checkpoint 数据库 `tradewind_workflows.db`。

已加入外联队列的文案和已持久化的生成历史会保留；尚未入队的审批草稿需先自行复制保存。恢复时把目标电脑旧 checkpoint 数据库连同其运行侧文件移入本地回滚目录，再以空库重新开始，防止旧工作流关联到恢复后的同名客户或重放持久化动作。这不改变正常运行时的 checkpoint 功能。

同机恢复保留当前模型、签名与邮箱配置；换电脑恢复需重新配置它们。禁止承诺业务正文绝不含秘密：用户可能曾把凭据粘贴进备注或邮件；本功能只排除配置与凭据存储，不清洗、改写业务内容。

### 3.4 敏感性提示

业务备份是含客户资料和邮件的普通 ZIP，不是脱敏诊断包，不上传网络，不进入 Git，也不随发行包发送。下载前明确提示妥善保管，不提交公开仓库。首版不提供密码保护；需要加密保管的用户可自行使用受控存储。

## 4. 文件格式与验证

ZIP 顶层为 `manifest.json` 与固定的业务路径。清单包含：格式版本 `1`、应用版本、UTC 创建时间、是否含照片、业务项存在标记、实际记录数量、文件相对路径、字节数和 SHA256。

清单不包含数据根绝对路径、设备用户名、模型 Key、邮箱设置或业务正文。店名作为照片相对路径本身仍属于私密业务资料。SHA256 和 ZIP CRC 仅用于发现损坏，不代表来源可信或数字签名。

导入只接受本格式，不接受任意手工压缩的数据目录。先流式保存到服务端拥有的临时目录，再验证，不能直接解压到运行数据目录。

验证必须覆盖：

- 清单版本、文件实际集合、长度、哈希、CRC 和从真实内容重新计算的数量；未知条目、缺失条目或重复条目拒绝。
- JSON 必须按业务项严格解析，验证类型、必需字段、ID 唯一性；不能用现有宽松读取函数把损坏数据当空列表。
- SQLite 使用只读连接检查完整性，并核对业务表、列、约束和索引。禁止未知表、视图、触发器、虚拟表或扩展加载；不调用上传数据库中的脚本，不反序列化 checkpoint。
- 按当前业务允许值验证外联渠道/状态、跟进渠道/结果、安排日期/状态、删除防重标记，以及每客户单一有效安排和每客户/渠道单一活动任务。
- 跟进记录、安排和删除防重标记必须引用备份中的客户；原有外联和历史允许保留已删除客户的名称快照，不作错误的外键清理。
- 客户、记录、安排、workflow ID 和 SQLite 自增序列保持不变，不重新编号或按名称关联。
- 已知旧应用版本只有在实际 schema 验证和受测兼容转换通过时接受；不只靠版本号猜兼容。未来格式或未来 schema 拒绝并提示使用更新版本。

所有相对路径按 Windows 语义验证：拒绝绝对路径、盘符、UNC、`..`、反斜杠绕过、空组件、ADS 冒号、控制字符、设备名、尾点/尾空格以及大小写或 Unicode 规范化后的重名。拒绝 ZIP 中的链接条目，也拒绝目标与来源路径中的符号链接、junction 和其他重解析点。每次文件操作重新确认目标位于允许的数据目录内。

初版资源上限：上传 ZIP 2 GiB、总解压量 8 GiB、普通文件 20,000 个、单张照片 20 MiB、单份 JSON 32 MiB、单个数据库 512 MiB、清单 8 MiB。逐块统计实际读入/解压量，不能仅信 ZIP 声明；超限报错，不能截断成不完整备份。导出同样执行这些限制。

创建、预览和恢复前检查可用空间，预算覆盖新归档、验证暂存、救援归档及 256 MiB 余量；原文件通过同卷移位保留，不当作已经可回收空间。空间或路径长度不满足时拒绝操作，保留原数据。处理图片和归档不一次装入内存。

## 5. 一致性与运行隔离

当前客户锁只保护客户与跟进，不能直接当成全局备份锁。产品、模板、历史、外联、爬虫和照片写入以及读取时建表都必须纳入维护协调。

新增小型维护协调器，统一登记会读写业务文件的请求和后台工作线程。后台任务的登记生命周期覆盖实际文件写入、收尾和取消退出，不只检查 UI 的任务状态字符串。正常模式保持原有任务能力，不把独立任务无关地串行化。

备份开始时原子关闭新写入/任务入口；发现爬虫、生成、OCR、照片识别、SMTP 提交或其他业务操作仍未退出，立即返回“请等待任务结束”，不强杀任务、不打断 SMTP、不在后台排队等待。维护请求与任务创建的竞争必须保证只有一方获得执行权。

没有活动工作时取得独占维护租约。临时阻止业务读取/修改、数据库懒初始化及新任务，仅保留静态页面、健康/维护状态、备份进度和必要取消接口。其他窗口收到可理解的维护提示，不显示假空名单。

在租约内严格读取 JSON，使用标准库 SQLite `Connection.backup()` 创建独立数据库快照，复制可选照片到拥有的暂存目录，并验证暂存内容。不能直接复制运行中的数据库文件，也不能独立读取 JSON 和 SQLite 后拼成不同时间点的归档。快照完成即可释放租约；压缩、下载从不变的暂存快照读取。

外部脚本直接改文件不受进程内租约保护。导出前后比较来源集合与文件状态，检测到变化即放弃；文档明确禁止同时运行直写数据的 CLI/第二后端。首版不声称提供跨进程或恶意本地用户的隔离保证。

## 6. 恢复流程与失败回滚

1. 用户选 ZIP。上传和验证在业务数据之外进行，不修改当前名单、数据库、照片或配置。
2. 预览展示备份日期、应用版本、客户/产品/模板/跟进/安排/历史/队列数量、照片是否包含，以及当前对应数量与将被替换的项目。数量从验证内容计算，不信清单单独声明。
3. 二次确认明确“替换当前业务资料”“不回滚设置”“禁止联系规则取并集”“未审核草稿与运行任务不恢复”“可发送邮件需核查”。输入“恢复”后才可提交；取消不会改数据。
4. 提交重新取得维护租约并重新核对当前数据版本及业务修订号。普通业务写入递增维护协调器的修订号，预览绑定它；预览后发生写入就要求刷新预览，避免用过期的数量确认替换。使用服务器生成的预览标识，只能操作已验证的暂存快照；拒绝过期、另一个数据根或已替换的预览，不能用用户提供的文件路径定位。
5. 自动生成当前业务数据的完整救援 ZIP，始终包含当前照片并按相同规则校验。只要救援失败、当前业务损坏或超出首版限制，就不准备恢复；原数据不变，提示人工停机备份。
6. 保存准备标记和恢复事务日志，进入“等待重启”维护状态。用户可以取消准备恢复，或关闭并重新启动程序；不自动终止进程、不自建隐藏重启服务。救援 ZIP 保留，且可在设置页下载。
7. 新进程在业务模块打开数据库、填充默认样例和执行外联/跟进启动清理之前处理恢复。只允许路径/config 的只读初始化；不得在恢复前触发 SQLite 建表、checkpoint 连接或孤儿清理。
8. 原白名单文件、被替换照片及旧 checkpoint 侧文件同卷移位至恢复专属回滚目录；写入已验证的新文件，记录每步完成情况。所有路径都由程序生成，不使用归档中的任意目标路径。
9. 在新内存库执行禁止联系保护与外联核查规则，验证新业务数据整体关系；成功后持久化新的数据版本并提交完成标记，然后开放业务接口。
10. 任一步失败自动按日志逆序回滚原文件。重启遇到未提交的中间事务同样先回滚，而不是自动再次应用备份。回滚成功时启用原数据并显示恢复失败通知；无法完整回滚时停止提供正常业务服务并明确告警，不把半份新数据当成功。

不能声称多个 JSON、SQLite 和目录替换是一项文件系统原子操作。通过同卷移位、逐步日志、落盘顺序和故障注入证明崩溃可恢复。成功标记只能在所有替换与整体校验完成后写入。

救援 ZIP、回滚原件和操作日志只存本地。日志只包含操作阶段、随机操作 ID、计数与错误类型，不写业务正文或 Key。首版不自动淘汰救援备份；设置页可确认删除已完成且不再用于当前恢复的一组救援材料，范围包含对应 ZIP 与回滚原件，明确告知旧未审核草稿也会删除。不可删除活动暂存或唯一未解决的回滚材料，不能只删 ZIP 后遗留无法管理的大量照片副本。

预览暂存有效期 30 分钟、同一时间只允许一个预览。取消、过期或上传失败时删除程序拥有的暂存文件；进入准备恢复后不因时间过期删除回滚材料。若程序被关闭，下次启动仅清理未进入准备阶段的遗留暂存。

## 7. 外联与旧网页保护

### 7.1 禁止联系不能被旧备份解除

恢复时把当前有效禁止联系规则与备份规则按渠道和标准化目标取并集；重名项保留当前规则的理由与时间。恢复后的活动队列重新套用禁止规则并标为 `suppressed`。保留较旧备份中的禁止规则是保守选择，解除仍需用户在现有入口人工确认。

### 7.2 恢复不代表撤回真实消息

外部已经发送的消息不会因为恢复消失。备份时间之后的发送证据保存在救援备份中，不把它伪造进旧快照，也不依赖客户 `sent/replied` 字段证明真实发送。

- 恢复的邮件 `pending_review/opened/failed/sending` 统一转为 `unknown`，附恢复核查原因，保留原有 Message-ID 和时间信息；原来的 `unknown` 继续保留。
- 用户必须逐条检查发件箱，通过现有“确认已发送 / 确认未发送”流程处理，才能重审、换发件账号或重试。
- 恢复的 WhatsApp `pending_review/opened/failed` 转为 `skipped`，说明需核对聊天记录；通过现有“恢复待审核”再进行人工操作，不打开链接或发送消息。
- 已有 `accepted/sent_manual/replied/invalid/skipped/suppressed` 不凭恢复升格为送达/已读；禁止联系规则优先覆盖仍活动的项目。
- 当前客户不存在的旧任务仍保留历史快照，但禁止从它直接发起发送或 WhatsApp 打开；原历史保留规则不改变。

恢复后发送核查数量在结果页显示。新建任务仍经过原有逐条审核和 SMTP 账号检查；首版不添加自动续跑、群发或完整事件溯源。

### 7.3 旧页面不能改错对象

恢复可能复用数字记录 ID 或恢复曾删除的客户 ID。不能只清空前端列表，就允许旧面板的删除、保存、审批、发送或取消请求落到新数据。

增加本机数据版本标识，正常业务数据修改不改变它，成功恢复生成全新随机版本。前端每次新页面加载读取版本，并随所有变更请求发送 `X-Tradewind-Data-Epoch`；第一次恢复前缺少标识的旧本机脚本维持兼容，发生恢复后缺少或旧标识返回 409 并要求重新打开页面。校验在领取业务执行权时进行，不能在请求进入时检查一次后排队穿过恢复。

旧页面不得后台更新自身标识后继续提交旧表单。遇到版本变化保留用户输入供复制，但禁用修改并提示重新加载；新页面清理旧任务恢复编号，不把旧 localStorage 任务 ID 自动用于新数据。原 API 参数/成功响应保持兼容，新增拒绝条件在运维文档说明。标识是防误操作机制，不是密码或远程鉴权。

## 8. 设置页与 API 边界

在设置页“本地诊断与售后”附近新增独立“业务备份与恢复”卡，沿用现有纸色、按钮、危险确认框和视口内滚动。明确区分“导出诊断包”和“下载业务备份”，不新增 Tab。

界面包含：照片选项、备份大小预估与创建/下载、恢复文件选择与进度、预览数量、二次确认、等待重启/取消准备、恢复结果、救援备份下载及确认后删除。上传失败、空间不足、校验错误和维护冲突均可重试；失败不能显示空数据或“恢复成功”。键盘焦点、Esc、窄屏布局和离开确认复用当前规范。

建议新增接口集合：

- `GET /api/backup/state`：维护状态、数据版本、准备/完成/失败报告及可操作的救援条目摘要。
- `POST /api/backup/export`：创建本机备份任务，可选照片；返回随机操作 ID。
- `GET /api/backup/operations/{id}`：进度/错误阶段；不返回正文、Key 或服务器路径。
- `POST /api/backup/operations/{id}/cancel`：取消未进入准备恢复阶段的导出或导入校验，关闭工作线程并清理其拥有的暂存文件。
- `GET /api/backup/operations/{id}/download`：下载已完成归档，使用服务端拥有的文件映射，不接收路径。
- `POST /api/backup/preview`：限量上传 ZIP 后启动严格验证，返回操作 ID；从进度接口获取成功后的预览标识及摘要。
- `POST /api/backup/restore/prepare`、`POST /api/backup/restore/cancel`：带预览标识、数据版本和请求 ID，重复相同请求只准备一次。
- `GET /api/backup/rescues/{id}/download`、`DELETE /api/backup/rescues/{id}`：按随机 ID 下载救援归档或确认删除非活动救援材料组。

创建与导入沿用本地 Origin 防线；诊断接口不增加业务内容。上传请求逐块限流/限量，取消检测必须能终止尚未准备的解析或压缩。资源释放在成功、失败、取消和客户端中断路径都有测试。恢复材料只在私有数据目录内，不作为静态资源开放。

## 9. 模块与改动范围

- 新增纯本地备份模块：明确拆分归档/校验、维护协调、准备/启动恢复三个职责；启动恢复部分只依赖标准库与已解析路径，不导入模型、爬虫或发送器。
- `server.py`：新增薄 API、业务请求/实际后台线程租约、早期恢复入口和状态报告，不把归档逻辑全部塞入现有大文件。
- `app/outreach_store.py`：仅补充恢复时的保守状态转换与缺失客户发送保护，不改日常已知状态含义。
- `frontend/src/tabs/SettingsTab.tsx` 与独立备份组件：设置卡和确认流程；`api.ts`、`types.ts`、任务恢复模块接入备份类型与数据版本保护。
- 前端样式只新增现有主题内的预览、状态和进度布局；不重设计其他 Tab。
- `.gitignore`：排除本地备份、暂存、恢复日志、救援归档和数据版本文件；不删除任何现有业务文件。
- README/OPS-NOTES：备份范围、照片规则、重启方式、跨机配置、外联核查、恢复故障和旧脚本版本标识说明。
- 为新模块/API/网页增加离线隔离测试，后续在绿色版 smoke 中覆盖同一条恢复链路。

不修改视觉提示词、爬虫识别算法、话术内容、产品内容、日常发信签名规则或模型参数；不新增第三方依赖。仅恢复用户在界面明确选择并确认的归档时，允许白名单内的业务快照替换，不能作为开发维护时整体覆盖数据的授权。

## 10. 验收要求

所有自动测试使用临时根目录、随机回环端口和合成 JSON/SQLite/照片。不可读取用户真实资料、Key 或 Windows 凭据，不调用外部模型、爬虫、WhatsApp 或 SMTP。

1. 往返恢复保留客户 ID、全部跟进表、防重标记、当前安排、生成历史、队列、去重记录、产品和模板；关联与计数一致。
2. 照片可选且默认不勾选；含照片恢复完整替换，不含照片保留现有照片，缺失/空目录含义正确。
3. 配置、`.env`、凭据、日志、checkpoint、暂存和旧备份不进入下载 ZIP；同机恢复配置不变，跨机无配置时仍可安全展示资料。
4. 校验拒绝损坏 ZIP/JSON/SQLite、未来 schema、未知条目、伪造计数、重复 ID、越界引用、恶意路径/链接、触发器/虚拟表和解压超限；原数据字节不变。
5. 自定义内存库路径与磁盘空间不足明确拒绝；缺失数据项不偷偷保留旧文件或补入演示资料。
6. 任务启动、取消收尾、SMTP 提交、同时修改及读取建表与维护租约的竞争受测；不能产生跨时点备份或写入已移走的旧数据库。
7. 救援失败不进入准备；准备取消不替换业务；预览后业务改变要求重新预览；重复提交/丢失响应不生成多个恢复事务。

10. 恢复后旧网页的保存、删除、审批和发送请求均被拒绝；新页面正常工作，旧输入可复制，旧任务 ID 不自动复用。
